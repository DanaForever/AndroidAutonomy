01 · How it works

MobileRun at a glance

MobileRun lets a language model control a real Android or iOS phone from a plain text goal. It runs in one of two modes, depending on how hard the task is.

◆ Direct mode (FastAgent)

One agent

It reads the goal and acts right away. No planning. Best for simple one-step tasks.

goal → action → done

◇ Reasoning mode

Two agents

A Planner and an Executor work in a loop. Best for multi-step tasks that may need correction.

goal → plan → act → check → repeat

In reasoning mode there are 2 agents: a Planner and an Executor. Each has a different role, reinforced by its prompt.

02 · The two agents

Planner and Executor

The split keeps the smart planning in one place. The Executor just acts, so it cannot drift off the plan.

◇ Planner

Makes the plan

Its prompt: "track progress and devise high-level plans."

  • ▸ breaks the goal into small steps
  • ▸ checks the screen after each step
  • ▸ keeps a running memory
  • ▸ decides when the task is done
◆ Executor

Does one step

Its prompt: "you are a low-level action executor."

  • ▸ takes one subgoal at a time
  • ▸ finds the target on screen
  • ▸ performs one action as JSON
  • ▸ does not decide what comes next
The Executor still reads the screen to locate the target. What it must not do is judge the plan or pick the next goal. That job stays with the Planner. This keeps the two roles from blurring.

03 · How it sees the screen

Turning pixels into choices

To act, the agent must know what is on screen and where to tap. MobileRun labels the screen so the model can pick an element instead of guessing coordinates.

MobileRun reads the accessibility tree (the list of UI elements the OS exposes) plus a screenshot. Every element gets a number, drawn as a colored box on the screen. The model then says click(34) and the framework maps that number back to a real tap point.

Tree available

Elements have numbers. The agent taps by index.

{ "action":"click", "index":34 }
Tree blocked

Some apps hide it (Messenger, banking, games). A grid is drawn instead and the agent taps by pixel.

{ "action":"tap", "x":540, "y":1180 }
One flag, requires_coordinate_tools, decides which path is used. The same Executor handles both.
Under the hood
Who makes the boxes? A script, not a model. A script parses the accessibility XML tree and gives each element an index. On the phone, the Portal app draws the boxes as a visual aid. Screenshots can hide them. The model just receives the indexed list plus a screenshot.
How fine is the grid? 10 by 10. Lines are drawn every 1/10 of the width and height, and each line is labeled with its x= and y= pixel value.
Does the Executor get the gridded image? Yes. In coordinate mode the screenshot it receives has the grid drawn on it. The grid is added for the model only.
The flag and the tools requires_coordinate_tools is True only when the tree is blocked (the screenshot-only provider), else False. Coordinate tools tap by pixel: click_at(x,y), long_press, swipe(from,to). Index tools use click(index) and type(text,index).
04 · A worked example

Task: "turn on dark mode"

One run through reasoning mode. Watch control pass between the Planner and the Executor.

0
See the screen
The framework reads the tree, draws the numbered boxes, and saves the screen state.
1
Planner
Makes a plan: open Settings, then tap Display, then toggle Dark theme. Picks the first step.
2
Executor
Runs the first step: {"action":"open_app","text":"Settings"}. The result is saved.
3
Planner
Reads the new screen, sees Settings is open, and picks the next step: tap Display.
4
Executor
Finds element [12] "Display" in the tree and taps it: {"action":"click","index":12}.
5
Planner
Toggles Dark theme, confirms it is on, and marks the task done.
If this were an app with no tree (like Messenger), steps 2 to 5 would use a gridded screenshot and the Executor would tap by pixel position instead. The loop stays the same.
