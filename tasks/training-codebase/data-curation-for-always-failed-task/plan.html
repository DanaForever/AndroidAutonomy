Manual Data Curation for Always-Failed Tasks

Plan for a lightweight local screenshot coordinate picker, smooth ADB capture loop, simple raw trace format, and AI-assisted thought/action text generation for Phase 2b of SFT overfit on always-failed tasks.

1. Key Decision

Collect a simple raw manual trace first; convert to SFT later. We do not need to force the human curation tool to emit repeat_00_inst_000_succ.jsonl. The curation UI should optimize for speed and correctness while collecting screenshots, pixel coordinates, ADB commands, and action metadata. A separate builder can later render Qwen-style messages, normalized coordinates, thoughts, tool calls, and parquet rows.

This splits the problem cleanly: the UI is a fast annotation and ADB helper; the builder owns training-format compatibility.

2. Target Workflow

  1. Start or connect ADB to the emulator/device.
  2. Start a local curation server for one task.
  3. Open the browser UI at http://127.0.0.1:8765.
  4. Select or confirm the task session: task name, goal, budget, optimal steps, success criteria, and output directory.
  5. Press c or click Capture to pull the current device screenshot via ADB.
  6. Hover on the screenshot to inspect pixel coordinates and normalized Qwen coordinates.
  7. Press s to freeze the primary coordinate. For swipe, press e to freeze the secondary coordinate.
  8. Copy or run the generated ADB command, for example adb shell input tap X_PIXEL Y_PIXEL.
  9. Record the action into the raw trace with a short human note such as "tap Display" or "drag brightness slider to minimum".
  10. Repeat: capture next screenshot before the next action.
  11. After the side effect is verified, add a final terminate(success) action and click Save trajectory. The server writes a complete trajectory folder and increments the saved-trajectory count.

3. Coordinate Picker UI

3.1 MVP Layout

RegionBehavior
Task header Shows task name, goal, step budget, optimal step count, number of saved trajectories, and task success criteria. Success criteria should appear in two forms when available: human-readable text and copyable/runnable verification commands. This should be visible at all times so the operator does not curate against the wrong goal.
Screenshot viewport Displays the current PNG at a stable scale. Cursor hover shows crosshair, pixel coordinate, and Qwen-normalized coordinate. The UI must calculate coordinates from the image's natural dimensions, not the displayed CSS size.
Coordinate status bar Shows live coordinate, frozen primary coordinate, frozen secondary coordinate, image size, and current step number.
Action side panel Shows copy buttons for tap, long_press, swipe, type, keyevent, wait, terminate, and Qwen tool-call JSON.
Trace panel Shows recorded steps with screenshot filename, action type, pixel coordinates, generated ADB command, human note, and validation warnings. Includes Save trajectory, Start next trajectory, and Discard trajectory controls.
Success criteria panel Shows the task-specific pass condition, verification checklist, and command snippets such as adb shell settings get system screen_brightness. Each command has Copy; safe read-only commands may also have Run and display stdout inline.

3.2 Keyboard Contract

KeyAction
cCapture current screenshot from ADB and load it as the current step screenshot.
sFreeze the current hover point as the primary coordinate.
eFreeze the current hover point as the secondary coordinate for swipe.
rClear frozen coordinates for the current step.
aAppend the selected action to trace.json.
nAdvance to next step after recording an action.
Ctrl+sSave the current trajectory after a terminal success action exists.

3.3 Coordinate Rules

ADB commands use physical screenshot pixels. Qwen tool calls use the model's normalized 999x999 coordinate system. Store both in the raw trace.

x_qwen = round(x_pixel * 999 / screenshot_width)
y_qwen = round(y_pixel * 999 / screenshot_height)

For a swipe, apply the same conversion to both endpoints.

3.4 Generated Commands

adb shell input tap X_PIXEL Y_PIXEL
adb shell input swipe X1_PIXEL Y1_PIXEL X2_PIXEL Y2_PIXEL 400
adb shell input text 'escaped_text'
adb shell input keyevent KEYCODE_BACK

If a device id is configured, the server can also show the fully qualified form: adb -s emulator-5554 shell input tap X_PIXEL Y_PIXEL. The copy button should default to the shorter form requested above.

4. Smooth Screenshot Capture

4.1 ADB Startup

The server should not assume ADB is already healthy. On startup it should run a small preflight and show the result in the UI header.

# Option A: Android emulator already running
adb start-server
adb devices -l

# Optional, when multiple devices are attached
export ANDROID_SERIAL=emulator-5554
adb -s emulator-5554 wait-for-device

# Basic readiness checks
adb -s emulator-5554 shell wm size
adb -s emulator-5554 shell wm density
adb -s emulator-5554 exec-out screencap -p > /tmp/manual-curation-probe.png

If no device is attached, the UI should show a blocking ADB offline state with the exact command output from adb devices -l. If more than one device is attached and no --device is passed, fail fast and ask for an explicit serial.

4.2 Recommended Architecture

A plain static HTML file can display an uploaded image and copy commands, but it cannot run adb or reliably access the clipboard from file://. The practical setup is a tiny local Python server plus a single HTML page.

python3 tools/manual_curation/serve.py \
  --device emulator-5554 \
  --task SystemBrightnessMin \
  --task-config tools/manual_curation/tasks/SystemBrightnessMin.json \
  --out training/data/manual_curation/raw

The server exposes only localhost endpoints:

EndpointPurpose
GET /Serve the HTML coordinate picker.
GET /device_statusReturn ADB serial, connection state, screen size, density, and last preflight error.
GET /taskReturn task name, goal, budget, optimal steps, success criteria, verification commands, saved trajectory count, and current trajectory id.
POST /captureRun adb exec-out screencap -p, write screens/step_NNN.png, return image URL and dimensions.
POST /record_actionAppend one action to trace.json.
POST /run_adbOptional convenience: execute the generated ADB command after explicit button click.
POST /save_trajectoryValidate and atomically finalize the current trajectory as trajectories/traj_XXXX/trace.json.
POST /new_trajectoryCreate the next empty trajectory folder for the same task.
GET /traceReturn current trace for refresh/recovery.

4.3 Capture Loop

  1. Before each action, press c. This captures the screenshot the model would see before acting.
  2. Pick coordinates and record the action.
  3. Run the ADB command from the terminal or from the UI.
  4. Wait for UI state to settle.
  5. Press c again for the next pre-action screenshot.
The screenshot belongs to the state before the action, not after it. This matters because each SFT row trains "given this screenshot, produce this action".

4.4 Automatic Trajectory Save

The UI should continuously autosave a draft after every screenshot capture and recorded action. The draft path is stable:

training/data/manual_curation/raw/SystemBrightnessMin/.draft/trace.json
training/data/manual_curation/raw/SystemBrightnessMin/.draft/screens/step_000.png

When the operator clicks Save trajectory, the server validates the draft and moves it atomically into the next trajectory id:

training/data/manual_curation/raw/SystemBrightnessMin/trajectories/traj_0000/trace.json
training/data/manual_curation/raw/SystemBrightnessMin/trajectories/traj_0000/screens/step_000.png
training/data/manual_curation/raw/SystemBrightnessMin/trajectories/traj_0000/screens/step_001.png

The save should fail with a visible error if any required condition is missing:

  • Task metadata is present.
  • At least one non-terminal action exists.
  • Exactly one final terminate(success) action exists.
  • Every non-terminal action has a screenshot.
  • Every coordinate action has in-range pixel and Qwen coordinates.
  • The operator checked success verified and optionally entered verification evidence.

After a successful save, the UI increments # trajectories saved, clears the draft, and starts traj_0001 for the same task.

4.5 Fallback Without Server

If we want an even smaller MVP, use a static HTML page with drag-and-drop image loading and this shell loop:

mkdir -p /tmp/manual-curation
adb exec-out screencap -p > /tmp/manual-curation/step_000.png

This is enough for coordinate picking, but capture and trace saving remain manual. Use it only for validating the UI math.

5. Raw Trace Format

Store one trace.json per successful demo. The trace is human-editable, easy to diff, and not tied to the current SFT build script.

{
  "schema_version": "manual_trace_v1",
  "task_name": "SystemBrightnessMin",
  "goal": "Turn brightness to the min value.",
  "trajectory_id": "traj_0000",
  "budget": 10,
  "optimal_steps": 3,
  "success_criteria": "The Android system brightness setting is at the minimum value and the task evaluator would pass.",
  "success_checks": [
    {
      "label": "Read system brightness",
      "kind": "adb_shell",
      "command": "adb shell settings get system screen_brightness",
      "expected": "minimum value for this emulator image"
    }
  ],
  "verification": {
    "success_verified": true,
    "method": "adb shell settings get system screen_brightness returned 1"
  },
  "device": {
    "adb_serial": "emulator-5554",
    "screen_width": 1080,
    "screen_height": 1920
  },
  "steps": [
    {
      "step_index": 0,
      "screenshot": "screens/step_000.png",
      "action": {
        "type": "click",
        "pixel": [540, 1210],
        "qwen": [500, 630]
      },
      "adb_command": "adb shell input tap 540 1210",
      "human_note": "tap Display in Settings",
      "verified": true
    },
    {
      "step_index": 1,
      "screenshot": "screens/step_001.png",
      "action": {
        "type": "swipe",
        "pixel": [[930, 335], [85, 335]],
        "qwen": [[860, 174], [79, 174]],
        "duration_ms": 400
      },
      "adb_command": "adb shell input swipe 930 335 85 335 400",
      "human_note": "drag brightness slider to the minimum",
      "verified": true
    },
    {
      "step_index": 2,
      "screenshot": "screens/step_002.png",
      "action": {
        "type": "terminate",
        "status": "success"
      },
      "human_note": "brightness value verified at minimum",
      "verified": true
    }
  ]
}

Every non-terminal action should have a screenshot and either pixel coordinates, text, button, or wait duration. The final action for side-effect tasks should be terminate(success).

5.1 Task Config

The UI header should be driven by a small task config file, not hard-coded in the browser.

{
  "task_name": "SystemBrightnessMin",
  "goal": "Turn brightness to the min value.",
  "budget": 10,
  "optimal_steps": 3,
  "success_criteria": "System brightness is set to the minimum value.",
  "verification_hint": "Run adb shell settings get system screen_brightness and expect the minimum value.",
  "success_checks": [
    {
      "label": "Read system brightness",
      "kind": "adb_shell",
      "command": "adb shell settings get system screen_brightness",
      "expected": "minimum value for this emulator image",
      "safe_to_run": true
    }
  ]
}

The UI should render success_criteria as plain text and success_checks as command rows. Command rows should show label, command, expected result, Copy, and optionally Run when safe_to_run: true. Write commands or destructive commands should default to copy-only unless explicitly approved in the tool implementation.

6. AI Thought Generation

6.1 Principle

The AI should not choose actions. The human trace is the source of truth. The model only writes concise Thought: and Action: text that matches the screenshot and selected action. The builder then appends the deterministic tool call.

One curated trajectory can produce multiple SFT samples by varying the natural-language thought/action text and optionally applying tiny coordinate jitter to robust coordinate actions. The original human trace remains the canonical source; generated variants are derived artifacts with explicit provenance.

6.2 Input to Qwen3-VL-4B-Instruct

For each step, send:

  • Current screenshot image.
  • Task goal.
  • Previous recorded actions as short text history.
  • Current selected action object from trace.json.
  • Human note, if present.

6.3 Single-Step Prompt Template

You are helping convert a human Android demonstration into SFT data.

Write ONLY the natural-language Thought and Action fields for the next step.
Do not choose a different action. Do not change coordinates. Do not mention
coordinate numbers unless the action is a precise drawing or slider movement.

Rules:
- Thought: one concise sentence explaining why this immediate action is next.
- Action: one short imperative sentence describing the UI action.
- Use only what is visible in the screenshot, the task goal, and the provided action.
- If the screenshot does not support the provided action, output exactly:
  NEEDS_REVIEW

Task goal:
{goal}

Previous actions:
{history}

Provided action:
{action_json}

Human note:
{human_note}

Return JSON:
{"thought": "...", "action": "..."}

6.4 Multi-Sample Prompt Template

For augmentation, request several variants at once. Keep the provided action fixed at this stage; coordinate jitter should be applied by the builder after validation, not invented by the model.

You are helping augment a human Android demonstration for SFT.

Generate {num_variants} alternative Thought/Action pairs for the same fixed
Android action. Do not change the action type, target UI element, text content,
button, or coordinates. The variants should be semantically equivalent and
short. Avoid adding facts not visible in the screenshot.

Rules for each variant:
- Thought: one concise sentence.
- Action: one short imperative sentence.
- The action description must match the provided action exactly.
- Do not mention coordinate numbers.
- If the screenshot does not support the action, return {"needs_review": true}.

Task goal:
{goal}

Previous actions:
{history}

Provided action:
{action_json}

Human note:
{human_note}

Return JSON:
{
  "variants": [
    {"thought": "...", "action": "..."},
    {"thought": "...", "action": "..."}
  ]
}

6.5 Coordinate Jitter Policy

Coordinate jitter is allowed only as a builder-side augmentation after the canonical trajectory is validated. Do not ask the AI to make up new coordinates.

ActionAllowed JitterGuardrail
click, long_press Up to ±2 physical pixels in x/y, then recompute Qwen coordinates. Only if the target is a large stable UI element. Do not jitter tiny icons, text cursor placement, canvas drawing, or file-list rows near boundaries.
swipe Up to ±2 physical pixels on each endpoint. Only for forgiving gestures like dragging a brightness slider to an endpoint. Do not jitter path-sensitive drawing or map gestures.
type, system_button, wait, terminate No coordinate jitter. Only thought/action wording variants are generated.

Recommended initial multiplier: 3 text variants per step and 1 jittered coordinate copy for safe coordinate actions. This yields more rows without flooding the dataset with near-duplicates.

6.6 Example Output

{
  "thought": "I need to open the display controls so I can reach the brightness slider.",
  "action": "Tap Display in the Settings list."
}

6.7 Builder-Assembled Assistant Message

Thought: I need to open the display controls so I can reach the brightness slider.
Action: Tap Display in the Settings list.
<tool_call>
{"name": "mobile_use", "arguments": {"action": "click", "coordinate": [500, 630]}}
</tool_call>
Use the remote vLLM-served Qwen3-VL-4B-Instruct for thought generation. For one canonical sample use temperature=0.0. For wording variants use a modest temperature such as 0.4, while still rejecting outputs that change the target action.

6.8 Offline LLM Post-Processing Script

Thought/action generation should run as an offline post-processing pass, not during live curation. This keeps the curation UI fast and avoids blocking the human on remote model latency.

python3 training/data/manual_curation/generate_thoughts.py \
  --input-root training/data/manual_curation/raw \
  --output-root training/data/manual_curation/annotated \
  --vllm-base-url http://REMOTE_HOST:9000/v1 \
  --model Qwen3-VL-4B-Instruct \
  --num-variants 3 \
  --temperature 0.4 \
  --coordinate-jitter-px 2

This iteration supports only SystemBrightnessMin. Other manual tasks are intentionally out of scope until the brightness workflow is proven end to end.

7. Training Dataset Builder

7.1 Builder Responsibilities

  • Read training/data/manual_curation/raw/*/*/trace.json.
  • Read task metadata: goal, budget, optimal steps, success criteria, and verification evidence.
  • Validate screenshots exist and coordinates are in range.
  • Ensure the final action is terminate(success) for side-effect tasks.
  • Consume offline LLM annotations from training/data/manual_curation/annotated, or fail with a clear message if required thoughts are missing.
  • Optionally expand each canonical step into text variants and safe coordinate-jitter variants.
  • Render assistant messages with Qwen tool-call JSON.
  • Render user messages using the same prompt shape as eval: goal, text history, current screenshot placeholder.
  • Write either an intermediate QwenAgent-style JSONL or a final verl parquet.

7.2 Recommended Two-Stage Output

StageOutputReason
Stage A training/data/manual_curation/qwen_jsonl/{task}/repeat_XX_succ.jsonl Easy to inspect and compatible with existing validation concepts.
Stage B training/data/sft_manual_failed_v0/train.parquet Actual trainer input, with images embedded for remote training.

7.3 Validation Gates

  • Every screenshot opens as PNG.
  • Every click/long-press has exactly one pixel and one Qwen coordinate.
  • Every swipe has two endpoints.
  • Every Qwen coordinate is in [0, 999].
  • Every assistant message passes training/data/response_validation.py.
  • Per demo: at least one non-terminal action and exactly one final terminal action.
  • Generated variants preserve action type, text payload, button payload, and terminal status.
  • Jittered coordinates stay in bounds and are tagged with augmentation.coordinate_jitter_px.

10. Decisions and Deferred Questions

10.1 Decisions

  1. ADB actions: run-from-UI is accepted for speed. Keep a copied command visible for auditability.
  2. Storage root: use training/data/manual_curation.
  3. Builder output: write QwenAgent-style JSONL first, then parquet. JSONL gives an inspectable intermediate and keeps compatibility with existing validation checks.
  4. Thought generation: offline post-processing pass via generate_thoughts.py.

10.2 Deferred

  1. Augmentation multiplier: start with --num-variants 3 and --coordinate-jitter-px 2; tune after inspecting duplicate pressure in the first dataset build.
  2. Additional tasks: deferred. Keep the first pass focused on SystemBrightnessMin.
