§ 01Why this exists

The sft_v0 build spreads 2,250 steps over 97 tasks — roughly 23 steps per task. That is enough breadth to validate the build pipeline, and not nearly enough depth to teach a 4B model anything per task. The current plan validates the data path; this plan validates the training path.

Goal

Produce an SFT checkpoint that measurably overfits a narrow task list, so that the eval delta — base@10tasks versus SFT@10tasks — confirms the verl recipe, the chat template, the loss mask, and the vLLM round-trip all function end-to-end.

This is not a capability claim. The held-out generalization story comes later. The point now is a clean, loud, unambiguous signal that the trainer changes the model on the things we trained it on.

If the loss curve drops and the eval score doesn't move, something is wrong — and on the current dataset shape, we wouldn't see it.

§ 02Sizing n_task_combinations

The knob (suite_utils.py:130) controls how many parameterised instances of each task are constructed per run. Each instance is a fresh generate_random_params() draw under a deterministic per-instance seed.

Three forces in tension

ForceDirectionBound
Demonstration count per task↑ helps overfitwant ≥ 15 successful rollouts/task after dedupe
Emulator time↑ linear cost~3 min/instance × workers parallelism
Param-pool collisions↓ at large Ntasks with small candidate pools waste runs past N≈20-30

Yield model

Per-task expected yield, where p_succ is the base-model success rate on the task and r is the retry budget:

# expected successful rollouts per task, before dedupe
E[succ] = N · (1 − (1 − p_succ)^(1 + r))

For the tasks UI-Voyager generated successful rollouts on (see sft_v0/stats), p_succ ≈ 0.4–0.7. With r = 5 retries, the second factor saturates near 1.0 — so E[succ] ≈ N for the chosen tasks. Retries do the heavy lifting against the few harder ones.

Target
30per task
n_task_combinations

Why 30. Delivers ≈ 20–25 unique successful rollouts per task after retries and dedupe — comfortably above the ≥ 15 floor. Past 30, low-cardinality tasks (binary toggles, two-choice menus) start producing rollouts identical at the param layer; dedupe keeps them by seed, inflating the dataset with behavioural duplicates.

10 tasks × 30 combinations × ~3 min ≈ 15 emulator-hours. With 4 workers ≈ 4 wall-clock hours.

Budget under different worker counts

Decision

n_task_combinations = 30, task_random_seed = 42, RETRY_FAILED_TASKS = 1, FAILED_TASK_MAX_STREAK = 5. Run with NUM_WORKERS = 4 as default. Adjust downward only if a task in §03 is shown to have a candidate pool < 20; adjust upward only after seeing the first build's per-task yield.

§ 03Choosing the 10 tasks

Selection is a function over five axes. The cheapest path is to rank every task in eval_results/ by a composite score and pick the top 10 that also satisfy a diversity floor.

Selection axes

AxisWhy it mattersHow we measure
Existing demo coverage Tasks already known to produce successful UI-Voyager rollouts will continue to. Zero cold-start risk. Count of *_succ.jsonl in eval_results/ for that task, post parse-gate.
Trajectory length Want 8–25 steps — long enough to carry signal, short enough that 30 rollouts fit the emulator budget. Median step count from sft_v0 task list.
Param-pool cardinality Tasks with pool < 20 will saturate before N = 30 and inflate the duplicate count. Static inspection of generate_random_params in the task source.
Action diversity The loss mask must exercise more than just click. Want the 10 tasks to span ≥ 4 distinct action types. Action-type histogram of the existing rollouts for that task.
App diversity Picking 10 Markor tasks would teach one app's UI grammar. Want ≥ 5 distinct apps. Task-name prefix (Markor*, Files*, Contacts*, …).

Procedure (deterministic, no judgment calls)

  1. Score every task currently in sft_v0/stats. Composite = 0.5 · rollouts_after_dedupe + 0.3 · (steps in [8,25] ? 1 : 0) + 0.2 · log(param_pool_size). Compute in a small notebook against the manifest.
  2. Sort descending, then walk the list top-to-bottom and add tasks to the chosen set under two diversity guards:
    • App prefix must remain represented ≥ 1× by the end. If chosen set already has 3 from one app, skip further candidates from that app until the set hits 10 with ≥ 5 apps.
    • Action mix: by item 10, the set's pooled action histogram must include at least click, input_text, swipe, and one of system_button / long_press / open_app.
  3. Verify candidate pool size by reading each chosen task's generate_random_params. If any task has fewer than ≈ 20 distinct param combinations, drop it from the set and continue down the ranked list.
  4. Freeze the list in a new config file androidworld/eval/configs/demos_overfit10.yaml; commit it before the run so the choice is part of the manifest.

§ 05Execution procedure

Two distinct configs, two distinct roles. Training data wants many param variations from a strong demonstrator; eval wants one consistent measurement point per task.

Data gendemos_overfit10.yamlUI-Voyager30 / taskproduce diverse demos

Non-optional · step zero

Pilot the pipeline before launching the full run. Existing infrastructure is a hypothesis the first time a new parameter value passes through it. Run a five-minute scaled-down version, write down what the output should look like, then diff. Skipping this step once already cost ~11 emulator-hours for 10 recoverable rollouts instead of ~250 — see [[feedback-pilot-before-long-runs]] in memory and the retrospective entry in the project notes.

Concrete pilot for this plan:

  1. Author demos_overfit10_pilot.yaml with n_task_combinations: 3 and one task (e.g. ContactsAddContact).
  2. Write down expected output: eval_results/UI-Voyager/results/<TS>/ContactsAddContact/ should contain 3 distinct repeat_00_inst_000_succ.jsonl, repeat_00_inst_001_succ.jsonl, repeat_00_inst_002_succ.jsonl (or _fail variants), plus an images/ directory whose filenames embed the matching inst000/001/002 tags.
  3. Run with NUM_WORKERS=1 and the pilot config. ~5 min.
  4. Diff actual against expected. If files are missing, named differently, or share content — stop. Fix before launching the full run.
  5. Optional but recommended: rebuild the parquet from the pilot output with build_sft_v0_1.py --out-dir /tmp/pilot_check and confirm step count ≈ 3 × steps-per-rollout, not 1 × steps-per-rollout.
  1. Author both configs.
    • demos_overfit10.yaml — copy of UI-Voyager.yaml with tasks: [10 names] and n_task_combinations: 30. Leaves llm.model: UI-Voyager in place.
    • eval_overfit10_base.yaml — same task list, n_task_combinations: 3, llm.model: Qwen3-VL-4B-Instruct. Drives the baseline pass.
    • eval_overfit10_sft.yaml — identical to eval_overfit10_base.yaml except llm.model points at the SFT checkpoint's vLLM served-name. Same task_random_seed → matched 3-seed compare.
  2. Generate training data with UI-Voyager. 
    # vLLM serves UI-Voyager
NUM_WORKERS=4 \
CONFIG_NAME=demos_overfit10 \
MODEL_NAME=UI-Voyager \
N_REPEATS=1 \
RETRY_FAILED_TASKS=1 \
FAILED_TASK_MAX_STREAK=5 \
./run_android_world_local.sh

    ~300 instances, ~150–250 successful demos saved under sft_data_dir. Wall-clock ≈ 4 h on 4 workers.

  3. Rebuild the parquet. Use the new build_sft_v0_1.py (the v0 build is left untouched as a frozen artifact). It handles the per-instance filename scheme, dedupes by (task, seed, repeat, instance), and writes a deterministic 90/10 train/val split: 
    python3 training/data/build_sft_v0_1.py \
  --eval-results MARS-Voyager/eval_results \
  --out-dir training/data/sft_v0.1 \
  --val-frac 0.1 \
  --val-split-seed 42

    Outputs train.parquet + val.parquet under training/data/sft_v0.1/. The split is rollout-level and stratified by task — every task contributes to both splits, so val loss measures per-step prediction on unseen trajectories of seen tasks (the right signal for an overfit experiment).

  4. Eyeball the data. Render ~20 random samples as HTML to verify the format end-to-end before training time: 
    python3 training/data/preview_samples.py \
  --parquet training/data/sft_v0.1/train.parquet \
  --out-dir training/data/sft_v0.1/preview \
  --n 20 --stratify-by-task

    Open preview/index.html. Each sample page shows the screenshot, the raw messages (system / user / assistant), the chat-template-rendered string the processor will tokenize, and a colour-highlighted span over the assistant response so you can see which tokens contribute to the loss.

  5. Baseline eval — base Qwen. Serve Qwen3-VL-4B-Instruct on vLLM, run eval_overfit10_base.yaml with RETRY_FAILED_TASKS=0 (eval measures single-shot capability; retries would distort the metric and unfairly favour whichever model gets the friendlier retry conditions). 30 instances total (10 tasks × 3 combinations), ~1.5 h wall-clock on 4 workers. Summarise into baseline_scores.json as mean success rate per task: 
    python3 training/data/summarize_eval_scores.py \
  --csv MARS-Voyager/eval_results/Qwen3-VL-4B-Instruct/logs/<TS>/detailed_results.csv \
  --config MARS-Voyager/androidworld/eval/configs/eval_overfit10_base.yaml \
  --aggregate mean \
  --out training/data/sft_v0.1/baseline_scores.json
  6. Train. Hand to the SFT-training sub-task (out of scope). Pin checkpoint at training/checkpoints/sft_v0.1/.
  7. Trained eval — SFT Qwen. Serve the SFT checkpoint on vLLM. Run eval_overfit10_sft.yaml (already points at the SFT served-name). Same task list / seed / n_task_combinations: 3 and same RETRY_FAILED_TASKS=0 as the baseline pass → identical protocol, directly comparable mean rates. Summarise: 
    python3 training/data/summarize_eval_scores.py \
  --csv MARS-Voyager/eval_results/sft_v0.1/logs/<TS>/detailed_results.csv \
  --config MARS-Voyager/androidworld/eval/configs/eval_overfit10_sft.yaml \
  --aggregate mean \
  --model-label sft_v0.1@step_2000 \
  --out training/data/sft_v0.1/trained_scores.json
  8. Report delta. delta_rate = trained.overall.rate − baseline.overall.rate in [-1, 1]. Anything north of +0.30 is a clear plumbing-works signal; +0.50 or higher is the expected memorisation outcome. Also inspect per-task rate deltas — uniform improvement is the desired shape.

§ 06Risks & off-ramps

RiskSignalMitigation
Memorisation looks like learning Loss → ~0, but trained model fails on tasks held-in train. Plumbing broken. Step 7 evals on the same seeds as step 5. If trained model can't reproduce its own demos, we have a real bug, not a learning question.
Long-tail task dominates One task contributes > 25% of training steps (cf. MarkorDeleteAllNotes). Per-task row cap in build_sft_v0.py (e.g. cap at 600 steps/task). Recorded in manifest.
Param-pool collapse Post-dedupe rollouts < 20 for some task. Hand-write an enumerator for that task, or drop it from the list before training.
Emulator drift across runs Same task + same seed gives different end states across runs (e.g. emulator state pollution). AVD reset already happens per worker. If observed, page MARS-Voyager/CLAUDE.md's troubleshooting and require fresh AVD copy per repeat.
Base success rate too low After step 2, < 8 successful rollouts/task even with retries. The 10-task list contains a task too hard for Qwen3-VL-4B base. Swap it for the next ranked candidate from §03 and repeat step 2 for just that task.

§ 07Deliverable shape

The output of executing this plan is a single, named, reproducible dataset version that supersedes sft_v0 for the dummy-run experiment:

  • MARS-Voyager/androidworld/eval/configs/demos_overfit10.yaml — frozen task list and combination count for data gen.
  • MARS-Voyager/androidworld/eval/configs/eval_overfit10_base.yaml & eval_overfit10_sft.yaml — 3-seed eval configs, one per model.
  • eval_results/Qwen3-VL-4B-Instruct/results/<ts>/ — fresh rollouts.
  • training/data/sft_v0.1/train.parquet — built by build_sft_v0.py --out-dir training/data/sft_v0.1.
  • training/data/sft_v0.1/baseline_scores.json — per-task base-model mean success rate over 3 seeds.
  • SFT-trained checkpoint & matched-seed eval scores — produced by the training sub-task, evaluated under eval_overfit10_sft.yaml with the same task_random_seed.

Success criterion is binary and concrete: trained-vs-base per-task success rate, summed over the 10 tasks, is greater than zero by a clear margin. Anything else, including a falling loss curve, is not evidence the plumbing works.

Margin notes
On "all variations" Tasks expose generate_random_params as a sampler over named pools, not a closed enumeration. Bumping n_task_combinations approximates exhaustive coverage statistically; hand-written enumerators would be exact but per-task. Plumbing test does not need exactness.
On retries RETRY_FAILED_TASKS=1 with FAILED_TASK_MAX_STREAK=5 re-runs failed instances up to 5 times. Effective attempts per combination ≈ 1 + 5 = 6. Saturates yield against base-success ≥ 0.4.
On dedupe (task, seed) dedupe (parent plan, §1) drops repeats by seed, not by params. Behaviourally identical rollouts with different seeds are kept. Tolerable here; the duplicates reinforce overfit.
On step caps A 600-step per-task cap would clip MarkorDeleteAllNotes (35 steps × 30 ≈ 1050) and FilesMoveFile (31 × 30 ≈ 930). Add the cap before training, after confirming the post-build stats.
On the baseline file baseline_scores.json exists to anchor the eval delta. Without it, "did training help" becomes a vibes question. Same seeds, same scoring — the only honest comparison.
