SFT Overfit on Always-Failed Tasks

Feasibility test: can SFT overfit a tiny set of always-failed AndroidWorld tasks once we manage to scrape any successful demos for them? Mirrors the overfit-10 SFT run in shape but pulls data from a brute-force, high-temperature rollout pass.

1. Context & hypothesis

The overfit-10 SFT run showed that SFT can drive Qwen3-VL-4B to memorize 10 tasks from UI-Voyager demos when those demos exist. The 32 always-failed tasks are the opposite regime: UI-Voyager pinned at temperature=0.0 never passes them, so no demos exist to begin with.

Overarching question. UI-Voyager was trained on rollouts produced by base Qwen3-VL-4B-Instruct. If the base model never produced successes on certain tasks during data generation, UI-Voyager never saw demos for those tasks — and so never learned them. The always-failed cohort is precisely the candidate set for this story. If we can generate demos for these tasks (by any means) and SFT them into the model, and the model then performs them, the gap is data-volume, not capability. That would localize the bottleneck to the original data-generation pipeline.

Empirical update (Phase 2). Running base Qwen3-VL-4B-Instruct at T=1.0 for 50 rollouts per task yielded a three-way split (see §6 Phase 2 results): three tasks with usable success rates, two with zero successes. Same shape was observed under UI-Voyager. The single-lever brute-force hypothesis is falsified for the zero-success bucket.

Updated approach. Treat the cohort as three buckets, each with its own demo source:

  • Auto-collected demos — three tasks where base-Qwen at T=1.0 already produces enough successes.
  • Manually generated demos — three tasks where automated collection fails. Generated via scripted ADB replay or oracle-augmented agent (§7 Phase 2b).
  • Skipped — tasks that fail both routes within the pilot's compute budget; written up as out-of-scope, not blockers.

What this plan is not. Not a generalization test. Not a benchmark improvement claim. The output is a per-task yes/no: did SFT learn the demos we managed to scrape, by whichever route.

Phase 1 — Pre-flight todo

Two checks before any rollouts run. Neither is optional.

1.1 Verify sft_data_dir captures successes only

The pipeline assumption is that Qwen3VLAgent + EvalRunner write rollouts to sft_data_dir only after the task evaluator returns pass. If this gate doesn't exist, every brute-force episode would poison the training set with failures.

Read:

  • MARS-Voyager/androidworld/eval/agents/qwen_agent.py — locate the SFT write path.
  • MARS-Voyager/androidworld/eval/runner.py — locate the evaluator call and the success-conditional write.
If success-gating is absent, add it before Phase 2. Do not run brute-force first.

1.2 Confirm sampling varies at T=1.0

Pin one task, run two episodes at temperature=1.0 with the same seed. If the assistant outputs are byte-identical (vLLM caching, ignored sampling, etc.), the brute-force lever doesn't actually do anything. Diff the two JSONLs by hand on the first 5 steps.

# quick lever check
NUM_WORKERS=1 CONFIG_NAME=demos_overfit5_failed MODEL_NAME=UI-Voyager \
  ./run_android_world_local.sh  # after editing tasks to one task, n_task_combinations=2
diff -u eval_results/UI-Voyager/.../*_0.jsonl eval_results/UI-Voyager/.../*_1.jsonl | head -50

Author the data-collection config and run the full 100-episode sweep.

2.1 Config

Copy demos_overfit10.yaml to demos_overfit5_failed.yaml. Apply exactly these diffs:

Phase 2b — Manual demo generation todo

Three tasks — MarkorAddNoteHeader, SystemBrightnessMin, CameraTakePhoto — do not yield demos via automated brute-force. Bootstrap demos manually so SFT has training data for them.

2b.1 Generation strategies

RouteWhat it isCostRecommended for
A. Scripted ADB replay Python script per task. Issues adb shell input tap/swipe/keyevent in a fixed sequence; captures a screenshot with adb exec-out screencap between actions; assembles a JSONL in Qwen3VL-Agent format with templated reasoning text per step. ~30 min/task to author. 100% reproducible afterwards. Tasks with deterministic UI: SystemBrightnessMin (slider drag), CameraTakePhoto (tap shutter).
B. Oracle-augmented agent Extend task_hints to a per-step list. Each step appends its step-specific hint to the goal. The agent still chooses the action; the hint constrains it. ~1 day to extend the hint plumbing + author per-step hints. Tasks with parameterized state: MarkorAddNoteHeader (per-instance filename).
C. Record human input adb shell getevent in a background process; human drives the emulator with mouse/keyboard; post-process raw events to (timestamp, action) pairs. Tooling-heavy. Skipped for now. —
D. Hand-write JSONL Pull screenshots from a one-off run; hand-write the prompt and response (in Qwen3VL's action grammar) for each step; concatenate into JSONL. ~1 hour/task. No tooling. Last-resort safety net.

2b.2 Per-task plan

TaskPrimary routeFallbackAction sketch
SystemBrightnessMin A (scripted ADB) D Open Settings → Display → Brightness slider; input swipe from the right edge to the left edge of the slider rect; verify adb shell settings get system screen_brightness == 1; terminate(success). Slider coords are constant across instances.
CameraTakePhoto A (scripted ADB) D Pre-requisite: fix AVD snapshot first (dismiss "Entering camera mode" modal + disable pointer-location overlay, see ongoing debugging notes). Then: launch Camera intent with am start -a android.media.action.IMAGE_CAPTURE; tap shutter at known coords; verify MediaStore; terminate(success).
MarkorAddNoteHeader B (oracle-augmented agent) A with per-instance filename resolution Per-step hints: (1) "Open the Markor app from the launcher." (2) "Tap the file named '{filename}' shown in the file list." (3) "Tap the edit pencil to enter edit mode." (4) "Move the cursor to the top of the document and type '# ' followed by the desired header." (5) "Save and exit." Filename comes from task.params at episode start.

2b.3 JSONL format requirements

Generated demos must match the schema written by QwenAgent._save_sft_data so the existing sft-data converter can ingest them:

  • One file per (task, instance): {sft_data_dir}/{task_name}/repeat_{repeat:02d}_inst_{inst:03d}_succ.jsonl.
  • One JSON object per step, each with fields: goal, task_name, text_prompt, response, image (PNG bytes base64-encoded or path), is_success: true.
  • response follows the Qwen3VL action grammar: {"action": "click", "coordinate": [x, y]}, {"action": "type", "text": "..."}, {"action": "terminate", "status": "success"}, etc.
  • Step screenshots must be captured at the same resolution the runtime agent sees (no resize).

Recommended scaffolding: add MARS-Voyager/scripts/manual_demo_gen/ with one Python file per task and a shared _jsonl_writer.py module that handles screenshot capture, prompt construction (re-using QwenAgent._construct_prompt), and JSONL serialization.

2b.4 Target volume

10 successful demos per task × 3 tasks = 30 manual demos. Small enough to author in a day; large enough that overfit-style SFT has something to memorize per task.

After each manual demo is generated, replay it through the eval pipeline to confirm the JSONL parses correctly and the recorded actions reproduce the success when fed to the runtime. A demo the converter accepts but that doesn't replay is silently broken.

Pre-defined branches per task:

  • Auto cohort with ≥5 successes → proceed to Phase 4 with those demos.
  • Auto cohort with 1-4 successes → small demo set; either accept thin coverage or top up with Phase 2b. Decide per task.
  • Auto cohort with 0 successes → route to Phase 2b manual generation.

Goal at this checkpoint is to have a labeled, per-task SFT dataset where every task carries ≥5 successful trajectories — from any combination of auto and manual sources — before launching the training run.

Phase 4 — SFT training (30 epochs) todo

Reuse the sft-run pipeline verbatim. Only deltas vs overfit-10:

  • Input dataset: parquet built from the union of (a) sft_rollouts/ of the Phase 2 brute-force run and (b) sft_rollouts/ of the Phase 2b manual generators. Same JSONL schema; the sft-data converter doesn't care about source.
  • Per-task demo budget: keep up to ~20 demos per task to avoid task-imbalance (NotesTodoItemCount has 43, others have far fewer). Subsample if necessary.
  • Epochs: 30 (was 60). Demo count is much smaller; 60 epochs would memorize noise.
  • W&B run name: sft_overfit_failed_v0.1.
  • Checkpoint output: $CKPT_HOME/sft_overfit_failed/global_step_* → rsync to local.
Everything else — LR, batch, FSDP shape, optimizer, collator, eval_overfit10.yaml-style serving — copies from sft-run. Do not retune.

6. Risks & failure modes

RiskLikelihoodMitigation
sft_data_dir writes both passes and fails high Phase 1.1 reads the code and verifies the gate. If absent, fix before Phase 2.
Brute-force yields 0 successes for some tasks high Phase 3 gate. Contingency: temperature sweep, then drop or abort.
vLLM ignores temperature (caching / config) med Phase 1.2 diff check. If outputs are identical at T=1.0, fix the server before continuing.
Tiny SFT set diverges or doesn't converge med Watch W&B loss. If unstable, drop epochs further or lower LR. Don't add data — that defeats the experiment.
Base Qwen3-VL-4B-Instruct unexpectedly passes some of the 5 tasks low If base passes, the always-failed framing for that task is moot (base is weaker than UI-Voyager, which already failed). Note it and proceed; the SFT improvement is still measurable as Δ over base.
Temperature 1.0 produces malformed actions that crash the runner low Existing parser already handles parse failures as no-op steps; episode just fails. Monitor logs for unusual crash rates.
