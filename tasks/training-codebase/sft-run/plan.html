4. Decisions (frozen)

Why fsdp2 (and not Megatron / DeepSpeed)

What Megatron buys you: tensor-parallel + pipeline-parallel sharding for models that don't fit on a single GPU. It splits matmuls across GPUs and routes activations through pipeline stages.

Why we don't need it at 4B:

  • 4B params × 2 bytes (bf16) = ~8 GB weights. Fits on a single 40 GB card with room to spare.
  • FSDP2 already shards weights, gradients, and AdamW optimizer states across the data-parallel group. On 4 ranks: ~12 GB/rank for weights+grad+optim. On 8 ranks: ~6 GB/rank.
  • The pressure on a 40 GB card is activations, not parameters — and activation checkpointing + Ulysses sequence-parallel address that directly. Megatron's TP doesn't help much here.

Cost we'd pay for Megatron: a TransformerEngine build (which setup_remote_env.sh deliberately skips with USE_MEGATRON=0), a Megatron-LM dependency, more complex configs (TP/PP/VPP/CP), and basically zero throughput win at this scale on one node.

DeepSpeed ZeRO-3 is roughly equivalent to FSDP2 at this scale, but verl's day-one supported backend is FSDP2 and the stock recipes are written for it. No reason to deviate.

W&B port-forward recipes

The remote can't talk to api.wandb.ai directly because of a proxy. Solution: open an SSH reverse tunnel from local that exposes a proxy on the remote's localhost; point wandb at it via HTTPS_PROXY. Two flavours, pick one.

wandb on remote thinks it's talking to localhost:8888. SSH ferries the bytes back to your local box, which has unrestricted internet.

Uses OpenSSH ≥ 7.6 built-in dynamic reverse forwarding. No extra software needed.

# On LOCAL: open a SOCKS server bound on REMOTE's localhost:1080,
# with traffic exiting via your local box's network.
ssh -N -R 1080 user@remote-host
#   -N: do not run a remote command (just hold the tunnel open)
#   -R 1080: dynamic SOCKS forward on remote port 1080

# On REMOTE (in the training shell):
export ALL_PROXY=socks5://localhost:1080
export HTTPS_PROXY=socks5://localhost:1080
export NO_PROXY=localhost,127.0.0.1

wandb login            # one-time, paste your API key
bash training/scripts/run_sft.sh   # run training as usual

Caveat: some Python HTTPS clients ignore ALL_PROXY for SOCKS unless requests[socks] / PySocks is installed. wandb's underlying requests handles it if PySocks is in the env. If recipe A doesn't connect, switch to B.

HTTP CONNECT proxy on local; reverse-forward its port to remote. wandb's requests always honors HTTPS_PROXY=http://....

# On LOCAL: run a small HTTP proxy on :8888.
pip install pproxy
pproxy -l http://:8888 &        # or: tinyproxy / 3proxy / mitmproxy

# Open the reverse tunnel (binds remote:8888 → local:8888).
ssh -N -R 8888:localhost:8888 user@remote-host

# On REMOTE:
export HTTPS_PROXY=http://localhost:8888
export HTTP_PROXY=http://localhost:8888
export NO_PROXY=localhost,127.0.0.1

# Verify the tunnel before launching training:
curl -fsS https://api.wandb.ai && echo "wandb reachable via tunnel"

wandb login
bash training/scripts/run_sft.sh
Operational notes. The tunnel must stay up for the full training run — if your laptop sleeps mid-run, wandb just queues locally and resumes when reconnected, but a long disconnect can drop the run. Add -o ServerAliveInterval=60 to the ssh command to prevent idle disconnects, and consider running the tunnel under autossh or a tmux session on local. If the tunnel is down at training start, the script's WANDB_MODE probe falls back to offline automatically — you can rsync the offline run dir back later and wandb sync it.
Confirmed on this cluster (2026-05-10): the corporate proxy proxytc.vingroup.net:9090 actively blocks api.wandb.ai with 403 VG-Blockpage on the HTTPS CONNECT. So:
  • Online without a tunnel: not possible. Setting HTTPS_PROXY=http://proxytc... still hits the blockpage on POST/CONNECT.
  • SOCKS Recipe A is the only online path. The reverse SOCKS tunnel routes wandb traffic out via your laptop's network, bypassing the corporate proxy entirely. Use socks5h://localhost:1080 (note the h — DNS through tunnel) so wandb's hostname is resolved locally too.
  • For dry runs: just use offline. 5 min of training isn't worth tunnel-debugging time. Set WANDB_MODE=offline, ship the run, sync from local later. The launch script's auto-probe does this for you when reachability fails.

Mockup — training/scripts/run_sft.sh 
#!/usr/bin/env bash
# Phase 1 SFT run: Qwen3-VL-4B on training/data/sft_v0/train.parquet.
# Usage:
#   bash training/scripts/run_sft.sh                # full run
#   DRYRUN=1 bash training/scripts/run_sft.sh       # 1 step, smoke only
#   NUM_TRAINERS=4 SP_SIZE=1 bash training/scripts/run_sft.sh
#
# Shell flags:
#   -e            exit on any command failure
#   -o pipefail   propagate failures through pipes (so `cmd | tee` doesn't hide errors)
#   -x            print each command before running (good for run logs)
# NOTE: deliberately NOT using -u (nounset). conda's activate script reads
# unset internal variables; -u makes it crash. Same reason you commented it
# out of setup_remote_env.sh.
set -eo pipefail
[[ "${VERBOSE:-1}" == "1" ]] && set -x

REPO_ROOT=$(git rev-parse --show-toplevel)
cd "$REPO_ROOT"

# --- Env --------------------------------------------------------------------
: "${HF_HOME:=$HOME/.cache/huggingface}"
: "${CKPT_HOME:=training/checkpoints}"   # repo-relative; resolved against REPO_ROOT (we cd above)
: "${WANDB_PROJECT:=gui_agent}"
export HF_HOME CKPT_HOME WANDB_PROJECT
mkdir -p "$CKPT_HOME"

# W&B: try online first, fall back to offline if api.wandb.ai is unreachable.
#   - online:  needs outbound HTTPS to api.wandb.ai (NOT a port-forward — wandb
#              is a hosted service, you talk to it directly).
#   - offline: writes to $WANDB_DIR; later run `wandb sync $WANDB_DIR/wandb/offline-*`
#              from any machine that *does* have internet.
if [[ -z "${WANDB_MODE:-}" ]]; then
  if curl -fsS --max-time 5 https://api.wandb.ai >/dev/null 2>&1; then
    export WANDB_MODE=online
  else
    export WANDB_MODE=offline
    echo "[run_sft] api.wandb.ai unreachable — using WANDB_MODE=offline"
  fi
fi

NUM_TRAINERS=${NUM_TRAINERS:-8}
SP_SIZE=${SP_SIZE:-2}

EXTRA=()
if [[ "${DRYRUN:-0}" == "1" ]]; then
  EXTRA+=(trainer.total_training_steps=1
          trainer.save_freq=-1
          trainer.experiment_name=sft_qwen3vl_4b_dryrun)
fi

torchrun --standalone --nnodes=1 --nproc-per-node="${NUM_TRAINERS}" \
  -m verl.trainer.sft_trainer \
  --config-path "$REPO_ROOT/training/configs" \
  --config-name "sft_qwen3vl_4b" \
  engine.ulysses_sequence_parallel_size=${SP_SIZE} \
  "${EXTRA[@]}"
Why setup_remote_env.sh needed set -xeuo pipefail commented out: the -u (nounset) flag triggers an error on any unset variable, and conda activate internally reads variables conda hasn't set yet (e.g. $_CE_CONDA). Two clean fixes: (a) drop -u, keep the rest — set -eo pipefail still gives you fail-fast and pipe-failure propagation, which is 90% of the value; or (b) keep -u globally but bracket conda: set +u; conda activate "$ENV_PREFIX"; set -u. The script above takes option (a).
Hydra config-path note: verl's trainer entrypoint uses Hydra. --config-path + --config-name tells Hydra to load our file as the top-level config, which then merges over verl's defaults. If verl's CLI rejects this layout, fall back to the stock-recipe pattern of passing every key as k=v on the CLI — same effect, uglier diff. Resolve in the dry run.

Sync checkpoint to local todo

Eval needs the Android emulator, which only runs on the local box. So the trained checkpoint has to come back. Only the merged huggingface/ directory is needed — the FSDP shards stay on the remote (they're useless without the matching world-size).

Sizing

  • Qwen3-VL-4B in bf16 ≈ ~8.9 GB across 2 safetensors shards.
  • Plus tokenizer + processor configs (<5 MB).
  • Total transfer: ~9 GB. On a 50 MB/s link that's ~3 min; on 10 MB/s, ~15 min.

Sync command

# Run from local repo root. Both sides keep checkpoints inside the repo at
# training/checkpoints/ (gitignored — see note below).
REMOTE=thivt1@<remote-host>
REMOTE_REPO=/path/to/AndroidAutonomy          # wherever you cloned on remote
SUB=training/checkpoints/sft_qwen3vl_4b_v0/global_step_210/huggingface

mkdir -p "$SUB"

# -a: archive (preserve perms/times). -P: progress + partial resume.
# -h: human-readable sizes. --checksum: verify by content hash, not mtime.
rsync -aP -h --checksum \
  "$REMOTE:$REMOTE_REPO/$SUB/" \
  "./$SUB/"
Gitignore. Add training/checkpoints/ to .gitignore alongside the existing training/verl/ and training/data/sft_v*/ entries. Each kept ckpt is ~9 GB — must never get committed.

Verify the transfer

rsync's --checksum already validated content equality during transfer. As a belt-and-suspenders, compare safetensors hashes once more and confirm the file list is complete:

# On remote:
ssh "$REMOTE" "cd '$REMOTE_CKPT' && sha256sum *.safetensors *.json" | sort > /tmp/remote.sha256

# On local:
(cd "$LOCAL_CKPT" && sha256sum *.safetensors *.json) | sort > /tmp/local.sha256

diff /tmp/remote.sha256 /tmp/local.sha256 && echo "checkpoint sync OK"

12. Risks & failure modes

SeverityRiskSymptomMitigation
high Processor mismatch (build vs train) Loss-mask span misaligned by 1-2 tokens; loss decreases but generations are subtly malformed. Both build and train pin revision=ebb281e. Step 1.3 prints resolved version. Step 5.2 catches empirically.
high CUDA OOM on vision tower Crash mid-batch with peak memory near 80GB on the rank that drew the largest screenshot. Halve max_token_len_per_gpu (32k→16k). Last resort: engine.activation_checkpointing=true.
med Hydra config-path layout differs from stock recipe Trainer fails to find our YAML; falls back to verl-internal default. Fall back to all-on-CLI overrides matching the 2B example shell verbatim.
med vLLM can't load the merged checkpoint vllm serve errors on tokenizer/processor files missing from huggingface/. Manually copy chat_template.jinja, preprocessor_config.json, tokenizer*.json from HF cache into the merged ckpt dir.
low 105 steps too few; no learning signal Loss flat. Eval score == off-the-shelf baseline. Bump total_epochs to 5-10. Cheap. Phase 1 milestone is the pipeline, not the score.
low Eval-vs-train chat template drift Trained model wraps text slightly differently than the regex in qwen_agent.py expects. Build script enforces messages[-1].content == assistant_response. Step 5.2 catches residual drift before the 10-task run.

  • Done. Score recorded; if > 0, Phase 1 is done.

14. Porting to runai / H100

Superpod (A100 40GB) is the debug environment. Real training will run on the runai cluster with H100 80GB nodes. The settings in training/scripts/run_sft.sh are tuned for A100 40GB and are deliberately conservative. Below is what to change when moving over.

Hardware-dictated changes

KnobSuperpod (A100 40GB)runai (H100 80GB)Why
model.enable_gradient_checkpointing true false 80GB has headroom; activation recompute is a ~25–30% throughput tax we no longer need.
+model.override_config.attn_implementation sdpa (flash-attn wheel needs glibc 2.32; node has 2.31) drop the override → defaults to flash_attention_2 H100 nodes typically run a newer base image with glibc ≥2.34. Verify with ldd --version inside the runai container; if so, pip install flash-attn==2.8.1 works out of the box.
data.max_token_len_per_gpu 16384 32768 (start) → tune up 2× the per-GPU memory means roughly 2× the dynamic-batch token budget. Watch peak memory on the first few steps and push higher if there's slack.
data.train_batch_size (global) 32 64 or 128 With dynamic batching the effective micro-batch grows automatically when you bump max_token_len_per_gpu, but global batch is independent. Pick from the LR-schedule shape you want.
engine.ulysses_sequence_parallel_size 2 1 (most likely) SP was needed on 40GB to fit long sequences. On 80GB with the token budget above, a single-rank pass fits — fewer collectives, simpler topology.
CUDA_VISIBLE_DEVICES masking Mask GPU at PCI 47:00.0 (bad ECC) drop the mask Hardware-specific to sdc2-hpc-dgx-a100-004. runai allocates fresh GPUs.
NUM_TRAINERS 6 (8 minus 1 bad minus 1 to keep DP×SP even) Match the runai job's nvidia.com/gpu request (likely 8) Set via the runai job spec, then read into the script via env.

Things to not change

  • Pinned versions: transformers 4.57.3, verl v0.7.1, Qwen3-VL revision ebb281e…. Re-pinning is a separate experiment.
  • data.max_length: a property of the dataset, not the hardware. Re-tune it once (TODO below) and use the same value everywhere.
  • Optimizer block (optim.lr=2e-5, betas, weight decay, warmup): hyperparameters, decouple from hardware migration.
  • checkpoint.save_contents=[model,hf_model,extra]: still needed; eval reads hf_model/.
  • Reverse logic: do NOT remove the WANDB_MODE auto-probe — it makes the script portable between both clusters with no edits.

Migration checklist

  1. Confirm runai image has glibc ≥ 2.32 (ldd --version) and flash-attn==2.8.1 imports cleanly. If yes → drop the sdpa override.
  2. Confirm PVC layout: where the repo lives, where HF_HOME lives, where training/checkpoints/ lives. Update those env vars in the job spec, not in run_sft.sh.
  3. Pre-fetch the pinned Qwen3-VL snapshot into the PVC once (avoid every pod re-downloading 9 GB).
  4. Run the same DRYRUN=1 command on H100 first. If loss is finite and a checkpoint is written, scale up.
  5. Launch full run with the table values above. Compare first-100-step loss curve to superpod's run as a sanity check (same data, same model, similar curve modulo batch-size effect).
